Lab: What ECB Really Hides

The ECB Picture Test — Block Cipher Modes of Operation

Prepared by: MR. Rostami

Scenario

A software vendor advertises their new file encryption feature like this: "We use AES encryption, the same standard banks use. Once a file is encrypted, it is completely unreadable — no exceptions."

Your job is to test this claim. You will encrypt the same image twice, with the same cipher and the same key, but with two different modes of operation — and see whether the claim holds up.

Task 1 — Create a test image

This test needs a BMP file, not a JPG or PNG. Those two formats compress the image before saving it, which already breaks up repeated patterns in the data — there would be nothing left to see. A BMP stores every pixel exactly as it is, with no compression.

We will use a demo image that already ships with ImageMagick, a free image tool. It has large areas of flat, repeated color, which is exactly what we need.

magick logo: -resize 256x256 -type TrueColor -depth 8 BMP3:test.bmp
If the command is not found

ImageMagick may not be installed yet:

sudo apt update
sudo apt install imagemagick

On some systems, the command is called convert instead of magick:

convert logo: -resize 256x256 -type TrueColor -depth 8 BMP3:test.bmp

Open test.bmp now in an image viewer, so you remember what the original looks like.

Mark once done

✓ Done

Task 2 — Separate the header from the pixel data

If we encrypt the whole file, including the header, the result will not open as an image at all — the viewer needs the real width, height and format to even start drawing. So we only encrypt the pixel data, and leave the header alone.

A BMP header stores the exact byte offset where pixel data begins, in its first 14 bytes. Find it:

python3 -c "import struct; print(struct.unpack('<I', open('test.bmp','rb').read(14)[10:14])[0])"

This prints a number — usually 54 for a simple BMP like ours. Use it to split the file:

OFFSET=$(python3 -c "import struct; print(struct.unpack('<I', open('test.bmp','rb').read(14)[10:14])[0])")
dd if=test.bmp of=header.bin bs=1 count=$OFFSET
dd if=test.bmp of=pixels.bin bs=1 skip=$OFFSET

You now have two files: header.bin (never touched again) and pixels.bin (what we will encrypt).

Mark once done

✓ Done

Task 3 — Encrypt the same pixels two ways

Use the exact same key both times — the only thing that changes is the mode.

1ECB mode:

openssl enc -aes-128-ecb -K 000102030405060708090a0b0c0d0e0f -in pixels.bin -out pixels_ecb.bin

2CBC mode (same key, plus an IV):

openssl enc -aes-128-cbc -K 000102030405060708090a0b0c0d0e0f -iv 000102030405060708090a0b0c0d0e0f -in pixels.bin -out pixels_cbc.bin

Notice: no password, no PBKDF2, no salt here. We are using a raw key directly, because we need full control over exactly what goes into the cipher.

Mark once done

✓ Done

Task 4 — Rebuild the images and look

Glue the original header back onto each encrypted pixel file:

cat header.bin pixels_ecb.bin > output_ecb.bmp
cat header.bin pixels_cbc.bin > output_cbc.bmp

Open both files in an image viewer:

xdg-open output_ecb.bmp
xdg-open output_cbc.bmp

If xdg-open does not work, open the files directly from a file manager, or with eog output_ecb.bmp.

Mark once done

✓ Done

Task 5 — Explain what you saw

One of the two images should still show a clear outline of the original picture. The other should look like pure visual noise, with no shapes at all — even though both were "properly" encrypted with AES.

Why does ECB leave the shapes visible?

Correct. Large flat-color areas in the image become many identical 16-byte plaintext blocks — and in ECB, identical input always gives identical output, so the outline survives.
Not quite. AES itself is the same strength in both modes — the difference is how blocks relate to each other.

Why does CBC hide the shapes?

Correct. The chaining step is exactly what breaks the block-to-block pattern that ECB leaves behind.
Not quite. The key is identical in both tests here — only the mode is different.

Why this matters

The vendor's claim was not false, exactly — AES-128 itself was never broken in this lab. But "we use AES" says nothing about the mode of operation, and the mode is what decides whether patterns survive encryption. ECB should never be used for anything beyond a single 16-byte block. This is also why real systems default to CBC, CTR, or GCM.
